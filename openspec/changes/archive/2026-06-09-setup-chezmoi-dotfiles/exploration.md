**Machine identity**: Hostname `cachyos-x8664`, Acer Aspire R3-431T (Celeron 3205U, 3.7 GiB RAM, btrfs, CachyOS rolling). The home directory has a substantial set of configuration files managed ad-hoc with no version control.

**What exists today**:

| Category | Configs Found | Managed? |
|----------|--------------|----------|
| WM/Compositor | Niri (279 lines, KDL format) + DMS auto-generated files (8 KDL files in `dms/`) | Manual, no VCS |

**Tool status**: Git 2.54.0 is installed. Chezmoi is NOT installed but available as `chezmoi` 2.70.5-1 in the `extra` repo (13 MiB download, 45 MiB installed).

### Affected Areas

- `~/.config/niri/dms/*.kdl` — auto-generated by DMS; must be **excluded** via `.chezmoiignore` (8 files: colors, layout, binds, alttab, cursor, outputs, windowrules, wpblur)
- `~/.config/fish/config.fish` — shell entry point; lightweight (12 lines), sources CachyOS system config
- `~/.config/fish/fish_variables` — universal variables managed by fish itself; must be **excluded** (not a source-of-truth, fish overwrites it)
- `~/.config/ghostty/config` — terminal emulator config (45 lines); Ghostty reads this directly
- `~/.config/alacritty/dank-theme.toml` — theme only; Alacritty may have other config elsewhere
- `~/.config/environment.d/90-dms.conf` — session environment variables; small, high-value
- `~/.config/systemd/user/niri.service.wants/dms.service` — symlink to system-installed unit; chezmoi must recreate the symlink
- `~/.config/yazi/` — multiple config files (lua, toml); potentially large and complex
- `~/.config/opencode/` — agent config (JSON, node_modules); partially auto-generated, partially user-authored
- `~/.config/superfile/config.toml`, `hotkeys.toml` — file manager configs
- `~/.config/micro/settings.json` — terminal editor config
- `~/.config/btop/themes/` — resource monitor themes; may be package-installed (verify before tracking)

- `/home/juan/misconfig/` — the SDD project repo itself; must NOT be tracked by chezmoi (self-referencing loop risk)

### Approaches

#### 1. **Approach A: Single repo, template-based per machine** (chezmoi-native, RECOMMENDED)

Use chezmoi's built-in templating (`{{ if eq .chezmoi.hostname "..." }}`) to handle machine-specific blocks within shared config files. One branch, one source of truth.

- **Pros**:
  - One repo to maintain — no merge dance across branches
  - Templates are self-documenting: machine differences are visible in-line
  - Chezmoi's `chezmoi data` can inject machine-specific values (font sizes, output names, DPI)
  - `.chezmoiignore` handles file-level exclusion cleanly
  - Industry standard — the chezmoi docs explicitly recommend this pattern
  - Git history is linear, not fragmented across branches
  - Adding a new machine = adding a template conditional, not a new branch
- **Cons**:
  - Template conditionals can become messy if machines diverge heavily
  - All machines share the same git history (no per-machine filtering)
  - Requires understanding go template syntax (`{{ if }}`, `{{ range }}`, `{{ .chezmoi.os }}`)
- **Effort**: Low-Medium

#### 2. **Approach B: Single repo, flat structure, manual overrides**

Store one version of each config with no machine-specific templating at all. Treat the laptop config as the "canonical" version. For future machines, manually maintain separate config files or use `.chezmoiignore` to skip incompatible files.

- **Pros**:
  - Simplest possible setup — just `chezmoi add` and commit
  - No template syntax to learn or debug
  - Works perfectly if machines are very similar
- **Cons**:
  - Doesn't scale past 2 machines without file duplication
  - Machine differences require entirely separate files (e.g., `niri-laptop.kdl`, `niri-desktop.kdl`)
  - How do you apply the right config to the right machine? Manual renaming or fragile scripts
  - Chezmoi has no native "pick this file for this machine" without templates
- **Effort**: Low initially, High long-term

#### 3. **Approach C: Branch-per-machine, merge shared configs**

Maintain a `main` branch with common configs and per-machine branches (`cachyos-x8664`, `workstation`, etc.) that branch from main and layer machine-specific changes on top. Merge shared changes back to main and rebase/cherry-pick to machine branches.

- **Pros**:
  - Familiar Git workflow (branching is well understood)
  - Each machine's state is self-contained in its branch
  - No template syntax at all
- **Cons**:
  - Merge/rebase hell when shared configs change across 3+ machines
  - Chezmoi's `init` always pulls from one remote/branch — you'd need per-machine init commands
  - Per-machine branches diverge over time; keeping them in sync is manual labor
  - Git history is fragmented — changes to shared configs appear in multiple branches
  - Anti-pattern in the chezmoi community; the tool was designed to avoid this
- **Effort**: High (maintenance overhead)

### Recommendation

**Approach A: Single repo, template-based per machine**, with a phased rollout:

1. **Phase 1 — Foundation**: Initialize chezmoi locally with `chezmoi init`. Track only the clearly portable, non-generated configs: fish, niri (root config only, exclude dms/), ghostty, environment.d. NO encryption yet (no secrets exist). Add `.chezmoiignore` with DMS exclusions and fish_variables.
2. **Phase 2 — Templates**: Add hostname-based conditionals only where actual machine divergence exists (today: none). Set up `chezmoi data` with a YAML/Toml data file for future machine-specific values (monitor names, font sizes, DPI). Template the git config when it's created.
3. **Phase 3 — Systemd & symlinks**: Track systemd user units (symlinks, not the service files which live in /usr). Chezmoi can recreate symlinks via its `symlink_` prefix or templates.
4. **Phase 4 — Expansion**: Add yazi, superfile, micro, btop configs incrementally — one tool per commit. Evaluate each for portability before adding. Create a GitHub remote when ready to share/sync.
5. **Phase 5 — Secrets (future)**: When secrets appear (API keys, tokens), add `chezmoi age` encryption. Not needed now.

**Why not the others**: Approach B fails at scale — the user explicitly said "múltiples equipos." Approach C fights against chezmoi's design and creates merge debt. Approach A is what chezmoi was built for.

### Risks

- **DMS regeneration**: DMS may change its generated file paths or format. Mitigation: `.chezmoiignore` patterns are already designed to exclude the entire `dms/` directory, so this is low-risk.
- **fish_variables tampering**: If `fish_variables` is accidentally tracked, chezmoi will fight with fish's own variable management. Mitigation: explicit `.chezmoiignore` entry + documentation.
- **Low RAM constraint**: chezmoi itself is lightweight (Go binary, ~45 MiB installed), but `chezmoi apply` processing many templates on 3.7 GiB is fine. No risk.
- **Rolling release drift**: CachyOS config paths may change. Mitigation: chezmoi templates can check `{{ if stat "/path" }}` before applying, or use `.chezmoiignore` conditionals.
- **Self-referencing**: The `misconfig/` project directory must be excluded from chezmoi tracking. Chezmoi watches `~/.local/share/chezmoi` by default, not `~/misconfig/`. Low risk, but document it.
- **No test runner**: Config validation relies on `niri validate`, `fish -n`, `systemctl --user check`. These are read-only commands — no risk of breaking the running system during validation. However, there is no automated test suite to catch regressions. Manual testing per apply is the workflow.

### Ready for Proposal

Yes. The exploration provides a clear recommendation (Approach A) with a phased rollout strategy, identified all configs to track/exclude, and documented the DMS auto-generation constraint. The next phase (sdd-propose) can proceed.
